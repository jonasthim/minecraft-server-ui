## Behavior and safety

- Administrator discovery uses the frozen `Discover(ctx, actor) (Discovery, error)` handoff. Both the service role gate and current database authority apply, including cached reads and responses after remote work. Empty trust remains unavailable.
- Only the configured repository's official `GET https://api.github.com/repos/{owner}/{repo}/releases/latest` is used. Current official GitHub documentation was checked on 2026-10-17: [Get the latest release](https://docs.github.com/en/rest/releases/releases#get-the-latest-release). The request supplies `Accept: application/vnd.github+json`, a fixed updater User-Agent and documented `X-GitHub-Api-Version: 2026-03-10`; it sends no credentials. GitHub's latest listing identifies its latest published full release, which need not be numerically greater than the installed version.
- Discovery has its own HTTPS-only transport pinned to `api.github.com`, with public-address checks on every dial and bounded redirects restricted to the exact original endpoint. Repository-move redirects require reviewed configuration changes. The asset client retains its original GitHub/asset host restrictions and cannot redirect or dial the API host. Response bodies are bounded to 1 MiB and remote work to 20 seconds.
- Drafts, prereleases, malformed JSON, duplicate members, deeply nested JSON, invalid UTF-8, missing required stable-state fields, invalid publication timestamps, malformed stable tags and uint64 version overflow are refused. Returned publication/check timestamps use UTC. Release links are constructed from validated repository and stable tag; upstream `html_url` is ignored.
- Titles are bounded to 256 UTF-8 bytes; notes to 65,536 UTF-8 bytes with `notes_truncated`. Notes render as escaped, keyboard-focusable plain text, including literal HTML/Markdown. Listing metadata and notes are labelled unsigned and confer no download/activation authority.
- One successful observation per service is cached for five minutes, including a successful 404/no-release observation. Expired successes never mask errors; failures are not cached. Concurrent requests share an in-flight result through a separate lock without holding the staging/activation mutex during network I/O. Waiting request cancellation does not abort the leader; leader cancellation cancels remote work and returns a shared failure for existing waiters, which can explicitly retry. Returned summaries are copied to protect the cache from caller mutation.
- Existing stable parsing and numeric comparison determine newer/same/older. Development and unknown/overflowing installed versions compare as unknown. A 404 becomes `no_release`, while transport/rate-limit/server errors remain failures.
- Discovery requires an explicit check and explicit version selection. It displays checked time, cache state, observation's installed version, release notes and comparison. Selection clears any previous signed check, selected stage and activation confirmation; manual exact-version check/download remain available. Signed metadata verification still precedes any download. Lost-stage-response reconciliation continues matching version/platform/schema/executable hash, and reload preserves verified stage recovery.
- Activation remains explicit. The acknowledgement wait is bounded to ten seconds; an accepted or transport-ambiguous response begins status-only polling for at most one minute, at two-second intervals with five-second request bounds. The UI shows waiting, cancellation, failure and the actual running version. It reports the requested version only after a new status response observes it. Rejection remains visible across status refreshes. Cancellation/navigation abort outstanding requests and timers. Polling never repeats activation and does not infer installed replacement from the apply HTTP response.

## Independent review fix round 1 — 2026-10-17

Read the complete independent `review-task32a.md` report. Important A1 identified an accepted activation whose acknowledgement is replaced by proxy HTML 502/504: the shipping API client maps these responses to `APIError('request_failed')`, which the page previously treated as a definitive rejection and excluded from reconciliation.

The apply catch now classifies transport errors, generic `request_failed`, and errors without a meaningful application code as ambiguous acknowledgements. It clears the selected stage, displays the unknown outcome, and starts the existing bounded status-only reconnect flow. Structured application rejections retain their original visible error and do not start polling. The ten-second acknowledgement limit, one-minute status deadline, request cancellation and prohibition on automatic apply replay are preserved. The shared API client, discovery backend and native update code are unchanged.

Focused browser regressions use the exact shipping API client with intercepted HTTP responses. HTML 502 and HTML 504 each failed before the fix on the missing unknown/waiting state. Both accepted-activation scenarios now require an explicit unknown outcome and cleared activation confirmation, observe a fresh status request, reject premature success while the manager is unreachable, and report the target version only after a fresh target-version status. Each asserts one apply request and stopped polling after reconciliation. Additional cases cover generic JSON `request_failed`, gateway ambiguity bounded by the existing one-minute deadline with no returned manager, and preserved definitive application rejection with zero background polling. A test timing race in a synchronous request-count assertion was corrected by waiting for the actual status request event.

Validation for this fix is scoped to the five gateway/application-rejection scenarios via `TASK32A_FILTER='gateway|explicit activation rejection'`, frontend TypeScript checking, lint on the owned self-update page/hook, and `git diff --check`.
