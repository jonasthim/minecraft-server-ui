Submitted for integrator review. This report does not accept the package, update the implementation ledger, qualify Minecraft combinations, or claim native Windows support. ## Delivered behavior

`internal/modpack` implements exact catalog selection, inert archive parsing, stored baseline/file hashes, deterministic old/local/new comparison, explicit conflict choices, persistent optional/pinned/excluded/disabled selections, source pack provenance, a customization summary, durable queued stopped application and recovery. There is no client pack export, arbitrary URL fetch, unknown ZIP import, world upload or adoption of an existing server directory.

The original publisher release and actual selected archive are separate: a CurseForge client release must have its official `serverPackFileId` mapping, or the selection must itself be an official server pack. The current private key remains mandatory through Task15; no shared key or inferred CDN URL exists. `Source.selection` preserves the original release/link; `artifact_selection` and SHA256 identify the actual downloaded/uploaded server archive. Both selections, metadata digest and archive hash are checked again before apply and receipt reuse.

A preview binds its actor/instance, current installed tuple, content revision, applied baseline revision, exact pack selection/metadata, staged postimages and actual local preimage hashes. Changed local configuration, deliberate missing files and modified upstream deletions require an explicit choice where both sides changed. Unchanged upstream files preserve local edits. Untracked local files are not adopted or modified. A retained removed file remains tracked as a local customization with an absent upstream baseline. Local item pins, disabled filenames, exclusions and optional choices persist. Individually installed content retains its catalog selection; bundled members carry `PackProvenance`, without inventing standalone catalog identifiers from filenames.

Manual acquisition covers both the outer official archive and required member files, including config/scripts/binary resources. An unavailable outer artifact creates a metadata-only preview: no verified pack SHA, changes, exclusions or parsed file plan are claimed. Administrator raw uploads bind to an exact catalog selection (and its official server-pack mapping) or an exact unresolved preview member; size and every supported published digest are checked before use. Unknown bytes cannot masquerade as a resolved file. Archive receipts bind actor, instance, original/actual selection, metadata, file size/hashes and 24-hour lifetime. Member receipts can be inherited from an actor-owned live preview only when pack selection, archive hash and metadata match; each member's current expected size/digests are rechecked. Superseded previews do not continue to block automatic updates. Live jobs/journals retain their references and cannot be discarded.

## Archive, path and transport policy

Before entry reads, ZIP central-directory allocation is bounded to a single-volume archive, 2 GiB input, 8192 entries and 8 MiB directory. ZIP64/multivolume, traversal, drive/UNC/ADS forms, control characters, unsafe Windows names, symlinks/nonregular entries, case collisions and file/directory collisions are refused. Expanded size is at most8 GiB, each file at most2 GiB, path depth12, and large-entry compression ratio at most200. Aggregate embedded text overrides are at most32 MiB, each at most1 MiB. The full archive is checked, including entries that will be excluded.

Modrinth format1/Minecraft root index is UTF-8 and bounded to4 MiB. Mandatory SHA1/SHA512 and declared file sizes are validated. Per-file dedicated-server `required`/`optional`/`unsupported` is distinct from the catalog version environment. Common overrides precede server overrides; client overrides are excluded. Unknown pack dependencies remain blockers. Minecraft/loader dependencies must match the installed tuple. Catalog server-unsupported versions remain blocked.

Activation allows `mods/*.jar`; bounded text under `config/**` and `defaultconfigs/**`; KubeJS `server_scripts`, `startup_scripts`, `data`, `assets`, `config`; and nested CraftTweaker `scripts/**/*.zs`. PNG/JPG/JPEG/OGG are allowed only under `kubejs/assets/**`, and NBT only under `kubejs/data/**` for add-on structures. `.mcmeta` is bounded UTF-8 text. Binary assets are streamed through existing staging limits. No host script/executable type, world root, runtime/library/control/manager location, server.properties/EULA, credentials location or another instance can be activated. CurseForge official server-pack ZIPs import only recognized roots and report excluded launchers/control/world entries; unknown directory trees are not imported. Arbitrary resources/globalpacks/openloader layouts remain unsupported.

The private mrpack-file transport accepts index-derived HTTPS URLs on exactly `cdn.modrinth.com`, `github.com`, `raw.githubusercontent.com`, `gitlab.com`. Each of at most5 redirects is revalidated; credentials, ports, query/fragment and traversal are refused. DNS answers must all be public; connections dial the checked IP, preventing a second unchecked resolution. No proxy, cookie jar or credential forwarding exists. Redirects to other CDN hosts require the digest-verified manual path. Downloads are bounded by the exact declared size and10-minute client timeout. Publisher SHA1 provenance is not upgraded into a stronger publisher assertion; local SHA256 is recorded separately.

Modpack staging limits are20000 records,8 GiB/instance and16 GiB across this feature, including archive receipts and rollback preimages. Previews cap at16 current records; previews/unused receipts expire after24hours. Referenced recovery data is retained. File+parent synchronization uses Task16 primitives; no unchecked duplicate file publication implementation remains.

## One transaction and retained stopped authority

`Register` adds `modpack_apply`; `Enqueue` creates one original durable job, protected by an instance/preview unique live-job index. It never calls `content.Enqueue`. The worker enters `Instances.WithStoppedJob` exactly once. `StoppedSession.WithTransactionScope` retains the original private session mutex/context throughout the participant callback and drains a callback already in flight before stopped admission can return. Copied, expired and overlapping session use is refused.

`content.WithPackParticipant` holds content admission under that retained scope, checks current actor/installed tuple/content revision, preserves unknown-trial provenance and validates the entire chosen candidate graph. The participant re-reads actual candidate JAR bytes/descriptors/published member hashes and refuses unmanaged JARs outside the proposed manifest. Its original-pointer/active/overlap checks expire the capability after the callback. `Commit` uses only the supplied SQL transaction; it rechecks actor authority, installed tuple/provisioning and expected content revision there. It cannot clear an unknown flag on preserved trial bytes. SQL must use FULL-or-stronger synchronous durability.

The coordinator owns one multi-file journal and independent `state/modpack-transaction.json` blocker. Stage files and parents sync before their receipts/journal become authoritative; the SQL journal commits before the boot marker, which syncs before publication. Each file publication checks its preimage and synchronizes the temporary file and parent. All postimages/manifest evidence are checked before the single SQL transaction commits content manifest, pack baseline, applied preview and committed journal together. The verified terminal file outcome is durable before clearing the blocker and journal. The coordinator closes its SQL transaction before subsequent service calls. These are the reuse boundaries for Task18; independent participant jobs are not a pack/update transaction.

Startup reconciliation requires paused dispatch and stopped recovery admission. It verifies the full journal preimage/postimage set before restoring any file. Unknown external edits, corrupt stages, malformed/foreign/orphan blockers and unsafe paths preserve the blocker for review. Committed transactions verify their postimages; interrupted transactions restore only recorded content/config preimages. World state is never restored automatically. Current authority failures, rejected manual acquisition, apply outcome and startup recovery outcomes are audited without content bytes, credentials or raw secrets. Native `CheckActivationReady` independently checks the marker, including boot before the manager.

## Compatibility extension and its limits

The root explicitly approved and pinned `github.com/pelletier/go-toml/v2 v2.4.3` (MIT, no added transitive modules). Typed parsing replaces the partial scalar TOML reader inside the existing256 KiB descriptor bound. Multiline descriptions/metadata no longer corrupt compatibility parsing. Forge dependency CLIENT applies to that dependency, and never marks the containing mod client-only; root `clientSideOnly` remains authoritative. Current NeoForge missing dependency type defaults to required. Historical NeoForge `mods.toml` with a declared `neoforge` dependency preserves its mandatory flags. Installed optional dependency versions are constrained. Multiple mod identities and declared ordering are preserved. The former test requiring every Forge FML range to be permanently unknown was deliberately changed: the language requirement must be preserved, and application remains denied without matching verified evidence.

The complete candidate is bounded to2048 content items,8192 identities and65536 dependency edges. Already-present fanout above128 is supported. Dependency cycles are allowed; explicit loading-order cycles are blocked. Required, optional and conflict constraints apply to all enabled identities in both directions. Disabled artifacts are preserved outside the active graph. Unknown trials retain their exact trial tuple and automatic-update blocker; they never waive a known contradiction or qualify automatic support.

Fabric string/array dependency expressions and provides aliases are preserved. Declared nested JARs are read inertly with depth4,2048 nested nodes,32 MiB/member and128 MiB aggregate bytes across the whole tree, plus collision/path/amplification checks. Nested identities, required/optional/conflict, Minecraft, Java and loader constraints are retained; client-only nested members are excluded from the server graph. Recommendations and soft conflicts currently receive conservative installed-version/conflict checks. Ambiguous duplicate identity/version selection is blocked rather than pretending to implement Fabric Loader's SAT selection. Unsupported version expressions remain blockers. Legacy Forge `mcmod.info` and Forge/NeoForge JarJar metadata remain unknown, not silently accepted. These are compatibility limits, not tested server support claims.

Java requirements are preserved and checked against the selected managed runtime major. Complex requirements that cannot be proven by the bounded numeric/range evaluator remain blocked; no exact JVM patch qualification is claimed.

FML evidence is separate from distribution version. The lifecycle adapter rejects pending activation/mismatched committed tuples, then calls the complete immutable-generation `VerifyLaunch` verifier. The loader adapter reads only receipt-pinned language artifacts. Forge javafmllanguage/lowcodelanguage require the actual language service and Implementation-Version metadata. Historical NeoForge support is narrowly pinned to Minecraft1.20.4/NeoForge20.4.253 and its reviewed FML loader2.0.17 library SHA256; its package Implementation-Version is2.0. Other NeoForge generations remain unresolved until exact provider/module evidence is implemented. Current documentation's javafml1 is not extrapolated to historical versions.

Delegated files beyond the primary ownership: new content participant/tests and narrow content types/descriptor/compatibility/service/preview/apply changes; new instance transaction scope/tests; new loaderutil and lifecycle language-evidence adapters/tests; new launcher marker checker/tests and the one activation hook. Root owns shared main, readiness/recovery composition, schema merge/generation, routes/navigation and ledger acceptance.
