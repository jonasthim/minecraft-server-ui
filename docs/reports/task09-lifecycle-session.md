## Current-job stopped-session API

```go
type JobMutationGuard interface {
    WithStoppedForJob(context.Context, *jobs.Execution, func(instanceID string) error) error
}

service := instance.New(database, paths, ordinaryIdleGuard,
    instance.WithJobMutationGuard(jobGuard))
err := service.WithStoppedJob(ctx, execution, func(session *instance.StoppedSession) error {
    detail, err := session.Detail(ctx)
    directories, err := session.Paths(ctx)
    requirements, err := session.RuntimeSettings(ctx)
    if err != nil { return err }
    _ = detail; _ = directories; _ = requirements
    return session.Materialize(ctx)
    // Provider artifact publication/activation belongs within this callback.
    // native.Start belongs after this callback, in the same serialized job.
})
```

The optional constructor parameter preserves existing constructor calls. Main must supply a typed guard that composes **execution.WithInstanceMutation → native.WithStopped → authoritative-id callback**, exactly once. The callback never trusts mutable public execution metadata. Ordinary CRUD and public `Materialize(ctx,id)` retain the existing idle-only guard; a running job still blocks them.

The original callback session pointer is the only usable authority. Private owner identity, active lifetime and context checks reject zero/forged/copied/retained sessions. Session methods reject concurrent operations. Callback exit, error and panic close further admission and drain any already-admitted method before releasing the native boundary. Caller and session contexts are combined for database/file operations. No global instance mutex is held across the provider callback; unrelated instance creation remains available while it runs.

Detail and paths are read-only projections. RuntimeSettings returns fresh typed desired native-rule requirements with the same lifetime check. Materialize calls the already-reviewed internal ownership/config-recovery path directly, without reacquiring queue or native locks. No unguarded exported mutation primitive was added. Missing current-job guard fails unavailable; forged/stale execution admission is denied by the jobs private identity boundary.

No main, jobs, native supervisor or lifecycle wiring was changed. Root owns final composition after review.

## Version-aware properties and forms

- Minecraft1.12.2/1.13.x use numeric difficulty and game mode: peaceful/easy/normal/hard =0/1/2/3; survival/creative/adventure/spectator =0/1/2/3. From1.14 the manager emits their names while retaining typed named values in desired configuration.
- Independent simulation-distance is emitted only from1.18. Earlier forms disable that input and explain that its desired value is not written for that version.
- Before1.21.9, desired PVP is written to server.properties. From1.21.9, the obsolete property is omitted. The required native runtime rule is `pvp` for1.21.9/.10 and `minecraft:pvp` from1.21.11, including the reviewed26.x family. MSMP remains disabled, and its disabled property is written only where the native protocol exists. RCON/query remain disabled.
- The property encoder filters manager-owned extras before version omission, so an unknown extra cannot reintroduce obsolete PVP/simulation or network controls. Existing unknown safe extras and the before/after-revision recovery semantics remain covered by the scoped suite.
- The seed description explicitly states that it affects new world generation only; changing it does not recreate or reset an existing world. No world NBT, reset or import operation was added.

`Detail.settings` is a derived settings projection. A viewer-gated read-only GET `/api/v1/instance-settings/capabilities?flavor=...&minecraft_version=...` exposes the same server-owned mapping to create forms, avoiding a second TypeScript version matrix. Structural runtime.Select validation rejects invalid flavor/version families; this is not a tested distribution/version qualification claim. Form requests cancel stale responses. The OpenAPI fragment and root schema contain only these owned instance-capability additions, and API types were regenerated by the documented command.

## Native PVP requirement handoff

`DesiredRuntimeSetting` contains Kind=boolean_gamerule, exact Rule, desired boolean Value, Source, applicable flavor/Minecraft/loader selection, Scope=all_discovered_worlds (a desired requirement; dynamic plugin worlds are not inferred covered by filesystem discovery), Supported, Reason, Status=unverified, Verification=native_rule_readback and GameplayEffect=not_verified. It contains no arbitrary command text, credentials or claim that anything was applied.

Task10/lifecycle must discover the actual native rule, apply the desired value to appropriate discovered worlds, and read it back. Failure of that required native setting blocks ready-for-use. Successful native-rule verification does not prove all plugin/mod gameplay effects. This package emits requirements only and never executes commands or writes world data.

Paper1.21.9/.10 supports the native pvp rule but its CraftWorld API can maintain a separate per-world plugin override. The projection includes that specific caveat; it does not reject a fresh official Paper server solely because such overrides are possible. Paper1.21.11's CraftWorld setter updates the native rule directly. Fabric/Forge/NeoForge use the upstream native rule mapping as an unverified requirement and disclose possible installed-mod overrides. Unknown software produces an explicit unsupported reason rather than an invented mapping. Known conflicting runtime/plugin overrides can be handled by later content/runtime integration; absence of a universal gameplay probe is not a native-rule failure.
